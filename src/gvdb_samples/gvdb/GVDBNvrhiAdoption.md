# Transactional host and exact atlas adoption

The private `GVDBNvrhiAdoptionInternal.h` seam prepares a complete replacement through the same authenticated `PreparedGeneration` and `NvrhiVolume::recordAndPublish` path. It is used by the serializer implementation, not installed as an external buffer-adoption API.

A request supplies a finished candidate `HostVolume`, exact brick-grid/apron dimensions, one unique leaf-index/slot pair per active leaf, complete channel descriptors, and each channel's complete logical raw bytes. Preparation validates the graph, supported GPU coordinate/address domain, placement, channel formats/counts/lengths and target CPU limits. It deep-copies candidate CPU pools and input bytes into private resources; later changes to the caller's candidate or byte arrays cannot change the ticket. CPU candidate atlas coordinates are discarded in the private clone; explicit slot records are authoritative for GPU placement.

Import deliberately differs from dense remapping. Original active slots are retained, and every logical byte is uploaded unchanged, including apron and unused-slot bytes. Only physical raw-buffer padding is zeroed. This preserves file data for immediate load/save round trips. Subsequent fill, clear, apron, copy, or dense repack operations follow their own documented unused-slot/apron rules; preserving imported bytes does not promise those bytes remain unchanged after an explicit edit.

The target host must be finished when preparing. The ticket captures target owner identity, host revision, channel configuration and publication serial. A later host edit/finish, channel change, or publication rejects the ticket before recording. Failed validation or allocation leaves the target host, current GPU generation and output ticket untouched. Host and channel replacements are fully staged; after recording uploads, publication swaps storage within the existing host object and assigns prepared channel/generation state without allocating or waiting.

`&owner.host()` remains stable across adoption. Every borrowed node/child/pool pointer expires, and the topology epoch advances beyond the previous target epoch. A bare `NodeId` does not carry an epoch or automatically detect stale reuse: callers must cache the corresponding epoch and reacquire IDs after replacement. Source candidate IDs retain their numeric pool order inside the new graph, but belong to the new target epoch. Old GPU snapshots retain their own placed CPU metadata and allocations.

`exportTopology` copies the retained generation's frozen placed node/child/level/map data without consulting the current host or waiting for GPU work. A save operation combines that exact generation with its own retained readback ticket, never with live host pools. Export and readback completion remain valid after owner destruction. `validateGeneration` compares the retained unique owner identity without allocating.

An optional immutable `IRHIObject` attachment is owned by the generation. The generic owner does not know file metadata fields. Serializer implementations can attach their private metadata object, recover it by private QI, and retain it in save tickets. Channel mutations and dense repacks within the same host epoch preserve the attachment. Host clear/reconfigure changes epoch and drops it; a new import replaces it atomically. Retained old generations retain their old attachments.

Configured-empty imports require a zero grid/apron and no nonempty channel data, matching the owner's no-live-atlas contract. A request with no active leaves and nonempty imported storage is rejected rather than silently discarded. The existing VBX serializer separately rejects unsupported empty-file layouts.

The independent adoption fixture uses signed active and inactive leaves, a 3 x 2 x 1 grid with non-dense slots 5 and 2, apron width two, and all five formats with nontrivial raw data. It checks exact apron/unused bytes, NaN payloads and signed zero, source-copy isolation, stable host identity, fresh epochs, partial allocation failure, malformed placements/channels, stale tickets, metadata retention/drop, frozen exports after later edits, and readback/export after owner destruction. Runtime validation results are recorded in the checkpoint after execution.
